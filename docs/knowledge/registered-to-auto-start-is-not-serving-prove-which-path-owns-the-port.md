## Trigger

You are about to retire one auto-start path in favour of another — or you are reasoning about "the companion is running" at all. Also bites when a health check passes and you assume you know *which* process answered it.

## Context

The companion can be started two ways: the Task Scheduler service (`ChodaCompanionServer`, logon trigger → VBS → launcher `.cmd` → `node dist/companion-server.cjs`) and the Electron app (HKCU `...\CurrentVersion\Run` → `Choda Companion.exe`, which bundles `resources/adapter/companion-server.cjs`).

Verified live 2026-08-06 (TASK-1442): **both were registered simultaneously**, and the state everyone assumed — "the Electron app is the launch path now" — was false. Port 7338 was held by pid 25456, `node C:\dev\choda-deck\dist\companion-server.cjs`, parented by `cmd /c companion-service-launcher.cmd`. The old service had been serving since 2026-08-04. The Electron app was not running at all.

When the service was removed and the Electron app launched on its own, it produced 5 processes bound only to ephemeral ports (53324/53325), never touched 7338, and `/healthz` refused the connection.

> **Correction, 2026-08-24 (TASK-1590).** The paragraph that used to follow drew the wrong conclusion from this, and the wrong conclusion outlived the observation by three weeks. It read: *"Its own log showed a long history of `[launcher] server exited -1073741205` (0xC000042B) restart loops interleaved with successful binds — so it had bound before and kept dying."* Both halves are false, and instructively so:
>
> - **The ephemeral ports were the app working, not failing.** `electron/adapter-launcher.cjs` spawns the adapter with `CHODA_COMPANION_PORT=0` **by design** (TASK-1437, to avoid colliding with this very service). The app has never bound 7338 and was never meant to. Only 7338 was probed, so a healthy adapter on a high port read as a dead one.
> - **The log was not "its own".** `[launcher] server exited … restarting in 15s` is emitted by exactly one thing in either repo — the `.cmd` generated by `scripts/install-companion-service.mjs`. The Electron launcher has no restart loop and emits no `[launcher]` lines. The two only appeared to share a log because `%APPDATA%\choda-deck-companion\data` is a **junction** pointing at `C:\dev\choda-deck\data`: the legacy service's crash history, read through Electron's userData path, looked like Electron's own.
>
> So the 0xC000042B crash belongs to the *legacy* launcher and remains unexplained; it is not an Electron defect. Verified live 2026-08-24: the app's adapter answered `{"ok":true}` on 127.0.0.1:62300 while nothing at all held 7338.
>
> The rule below survives this correction intact — it is in fact what *caught* it. What failed was applying rule (3) to the app: its port was never established, only assumed.

## Business rule

**Registration is not execution, and execution is not service.** Three distinct facts, none implying the next:

1. A path is *registered* to auto-start (scheduled task exists / Run key exists).
2. Its process is *running*.
3. That process *owns the port you care about*.

The Electron app satisfied (1) and (2) while failing (3), and looked entirely healthy doing it. A green `/healthz` proves only that *something* is listening — never which path put it there.

**Two registered auto-start paths can coexist silently, and the loser leaves no trace.** Nothing warns you; whichever binds first wins and the other simply never serves.

## Resolution

Establish ownership before drawing conclusions, on Windows:

```
Get-NetTCPConnection -LocalPort 7338 -State Listen        # who is listening
Get-CimInstance Win32_Process -Filter "ProcessId=<pid>"   # CommandLine + ParentProcessId
```

Do not assume the port, either: a host may bind an **ephemeral** port on purpose. Establish the port the same way you establish ownership — read it from the process, or from a file the host publishes (the Electron app now writes `<dataDir>/companion-port.txt`, TASK-1590). Probing a port the host never claimed is how a working adapter gets recorded as dead.

The **parent chain is the discriminator** — `cmd /c companion-service-launcher.cmd` means the Task Scheduler path; an Electron parent means the app. `CommandLine` alone is not enough: both hosts run a `companion-server.cjs` of identical size, so the bundle path distinguishes them but the process name does not.

Before retiring any fallback launcher, prove the replacement serves *with the fallback absent* — and prove it survives, not just starts. A crash-restart loop looks identical to health if you sample once inside a bind window. Sample twice, minutes apart, and check the log for `server exited` lines appended in between.

Corollary for the app itself: failing to host the adapter must surface in the UI. This went unnoticed for days precisely because the app appeared to run normally while serving nothing. Fixed in TASK-1590 — `watchAdapter` now raises a visible error on post-boot adapter death, where previously nothing watched the child once boot succeeded.
